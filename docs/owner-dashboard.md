
# Кабинет владельца WebDiag

Владелец входит через штатную форму WebDiag и открывает «Кабинет владельца» в настройках личного кабинета. Для кабинета предусмотрены два адреса на хосте приложения. [Русский](https://app.webdiag.ru/admin) · [English](https://app.webdiag.ru/en/admin)

## Назначение и отзыв доступа

1. Подтвердите, какой существующий аккаунт принадлежит владельцу. Получите его постоянный ID из поля `user.id` в авторизованном ответе `/api/account/me` или из записи `account_users` в согласованной копии SQLite. При чтении копии ищите точное совпадение нормализованного email параметризованным запросом.
2. Укажите этот UUID в `WEBDIAG_OWNER_ACCOUNT_ID` только для сервиса API.
3. Примените переменную при согласованном перезапуске API. Проверьте, что сессия назначенного владельца получает `200` на `/api/admin/access`, другой активный аккаунт получает `403`, гость получает `401`.
4. Для отзыва очистите переменную и перезапустите API. Для передачи полномочий укажите ID нового владельца и проверьте обе сессии.

Страницы для гостя и обычного клиента показывают локализованный экран доступа с HTTP `200`. FastAPI и BFF возвращают `401` для отсутствующей, истёкшей и отозванной сессии, `403` для действующей сессии без полномочий. Сбои чтения возвращают `503`. Страницы и API помечены `noindex` и `private, no-store`.

## Как считаются данные

| Показатель | Источник и границы |
| --- | --- |
| Регистрации | Одна запись `account_users` на аккаунт. Новые регистрации считаются по `created_at` за 7, 30 и 90 суток. Во вкладке «Клиенты» показывается факт регистрации, поскольку в модели нет отдельного статуса блокировки или единого статуса подтверждения почты. |
| Оплаченный доступ | Один текущий план на аккаунт из `billing_plan_periods` при `starts_at <= as_of < expires_at`. Смежные периоды того же плана продлевают срок. Скорое окончание означает `as_of < expires_at <= as_of + 7 суток`. |
| Подтверждённые оплаты | Время из `billing_payment_confirmations.paid_at`. Запись сохраняется в транзакции, которая подтверждает счёт, начисляет кредиты и при необходимости открывает период. Суммы хранятся в минимальных единицах и группируются по валюте. Список позволяет выбрать дату создания счёта, дату подтверждения или исторические счета с неизвестным временем оплаты. |
| Доступные кредиты | Текущая сумма `credit_accounts.available`. Клиентская строка показывает доступный баланс этого аккаунта. |
| ИИ | Логические `ai_runs`, созданные за период, в состоянии на момент чтения. Попытки из `ai_run_attempts` не увеличивают счётчик. Для удалённых запусков доступно текущее состояние `deleted`. |
| Аудиты | Записи, сохранённые пользователями в проектах за период. Общая база публичных проверок содержит анонимные задачи, которые нельзя надёжно приписать клиентам. |
| Мониторинг | Завершённые проверки в сохранённой истории. Хранилище сохраняет до 100 последних записей на монитор и удаляет связанную историю при удалении монитора или проекта. |

Сводка берёт один снимок SQLite и одну отметку UTC. Прошедшие интервалы включают начало и исключают `as_of`. Таблицы отображают даты в UTC. Счета, подтверждённые до появления отдельной записи о подтверждении, сохраняют статус оплаты и входят в счётчик «Оплачено без даты». Ручное начисление в журнале кредитов может использовать совпадающий `correlation_id`, поэтому этот журнал не доказывает время подтверждения. Сохранённого источника возвратов, споров и автопродлений нет.

## Схема и поставка

`SqliteBillingStore.ensure_schema()` создаёт отдельную таблицу подтверждений. Старый код может создавать счета на той же схеме. Оплаты, подтверждённые старым кодом после отката, будут отображаться без даты. При включённом кабинете API готовит схемы через существующие хранилища при старте. Защищённые GET открывают основной файл аккаунтов через SQLite URI `mode=ro` в короткой транзакции чтения. Для WAL используются обычные файлы базы, WAL и SHM на одном томе. Перед выпуском проверьте восстановление из согласованной резервной копии.

## Локальная проверка на синтетических данных

Из корня проекта после установки npm- и Python-зависимостей выполните команды.

    npm run build
    npm --workspace @webdiag/web run test:browser:owner

Playwright поднимает локальные Next.js и FastAPI на портах 4183 и 4184. FastAPI начинает с отдельной временной SQLite и регистрирует тестовые аккаунты. Кредиты, периоды, оплаты и записи ИИ создаются локально. Тесты проверяют штатный вход, роли, сводку и фильтры на реальных ответах API.

Для ручного просмотра запустите API в первом терминале.

    node scripts/run-python.mjs apps/api/tests/fixtures/owner_admin_demo.py

Во втором терминале PowerShell задайте адрес локального API и запустите веб-сервис.

    $env:PORT = '4183'
    $env:HOSTNAME = '127.0.0.1'
    $env:WEBDIAG_API_INTERNAL_URL = 'http://127.0.0.1:4184'
    $env:WEBDIAG_ACCOUNT_PUBLIC_ORIGIN = 'http://127.0.0.1:4183'
    $env:RESEND_API_KEY = ''
    npm --workspace @webdiag/web run start

Откройте локальный кабинет и войдите как `owner@example.test` с паролем `Synthetic demo password 293`. На обзоре откройте «Всего клиентов» и найдите `client@example.test`. Затем вернитесь в обзор и откройте срок истечения Pro. Карточки RUB и USD показывают отдельные списки подтверждённых оплат за период. Аккаунт `client@example.test` с тем же демонстрационным паролем открывает обычный личный кабинет и получает `403` на запросы владельца. [Локальный кабинет владельца](http://127.0.0.1:4183/admin)

## Источники архитектуры

В KPDesk взяты компоновка сводки, переходы к отфильтрованным таблицам, типизированные результаты и отмена устаревших запросов. SQLite-запросы, модель сессии, BFF и оформление используют код и тему WebDiag.

Context7 использован для Next.js App Router и `no-store` (индекс 16.4.5 для исходной установленной версии 16.4.2), FastAPI 0.139.1 и функциональной зависимости с общим SQLite-снимком, Playwright 1.61.1 и изолированных контекстов с общей cookie для браузера и его API-клиента. После первой сборки Next.js обновлён до 16.4.6 в той же ветке версий.
